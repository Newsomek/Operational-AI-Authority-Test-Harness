Scenario: what are we testing?

Default scenario: An automated refund system is being asked to issue a customer refund. Before conditions change, Operations has active authority to approve refunds up to $500 for LOW-risk customers.

Customer risk is the experimental variable, not the point of the experiment. To make the change concrete, imagine the customer has crossed a configured return-frequency threshold, such as a third return within 30 days. That trigger changes the customer's risk classification. The harness is not evaluating whether that risk rule is fair, accurate, or desirable; it simply uses the selected risk level as a controlled condition.

For this scenario, a change from the prior customer-risk classification to a different selected risk classification is treated as MATERIAL. That lets the experiment test what happens to organizational authority after a material condition changes.

What the experiment is testing: after the material change, what organizational authority — if any — exists, who is permitted to make the reauthorization decision, what execution boundary results, and whether the automated system is permitted to perform the requested refund.

What the experiment is not deciding: a BLOCK result does not mean the customer's refund is ultimately denied. It means only that this automated execution is not authorized under the authority currently in force. A real organization might escalate the request to another person, process, or authority level. That downstream decision is outside this experiment.

Reauthorization architecture

Same-layer reauthorization: the operational team running the process also retains authority to make the reauthorization decision after a material change.

Separated reauthorization: the operational layer detects the material change, invalidates prior authority, and blocks execution. A designated authority owner outside the operational layer then decides whether and how authority should be renewed, narrowed, conditioned, transferred, suspended, or refused.

The experimental variable is who is authorized to decide. Changing the architecture does not automatically change technical capability, evidence, the requested action, or execution permission. Separation does not itself create authority or prove a better outcome.

What do these controls do?

Use this guide when you are unsure which action to take. The same concise definitions also appear as button tooltips when you hover over a control.

Load default
Loads the standard baseline scenario into the editor and structured controls. Use it when you want a known starting point, when you have changed the scenario substantially, or before demonstrating the harness to someone else.
Import scenario
Loads a compatible saved scenario. Use it when you want to reproduce a prior setup, test a scenario prepared elsewhere, or compare multiple prebuilt cases.
Export scenario
Saves the current experiment inputs, not the run result. Use it to preserve a configuration, share it with another reviewer, or rerun the same scenario later.
Export run evidence
Saves the evidence generated by the latest completed experiment, including authority history, execution evidence, assertions, and replay inputs. Use it for review, audit, comparison, or reproducibility.
Reset
Clears the current working run state and returns the interface to a clean scenario state. Use it when the current experiment is no longer useful or before beginning a materially different setup.
Apply controls
Copies the visible structured inputs into the scenario data. Use it after editing the form when you want the Raw editable input to reflect those changes. It changes inputs only; it does not run the experiment or manufacture results.
Run Experiment
Executes the current scenario through the deterministic governed engines. Use it after your inputs are set. This is the main action for seeing what happens and why under the selected governance conditions.
Compare Architectures
Runs the same scenario twice while changing only the reauthorization architecture. Use it to test whether decision topology produces an observable difference while the scenario, evidence, requested action, capability, and disposition remain held constant.
Replay
Recomputes the most recent run from its causal replay inputs. Use it to confirm that the same evidence can reproduce the same governed result without using the recorded result itself as an instruction.
